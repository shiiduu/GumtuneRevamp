# Minecraft 26.1.2 API Notes

Findings from decompiling the real 26.1.2 client/common sources via
`./gradlew genSources` (Loom + Vineflower, Mojang mappings) and cross-checking
against `FabricMC/fabric-api` tag `0.155.3+26.1.2`. Nothing here is guessed or
carried over from pre-26.1 (Yarn-mapped) versions.

## Client tick lifecycle

| Class | Method | Purpose | Thread | Notes |
|---|---|---|---|---|
| `net.fabricmc.fabric.api.client.event.lifecycle.v1.ClientTickEvents` | `START_CLIENT_TICK` / `END_CLIENT_TICK` | Fires once per client tick with `Minecraft` instance | client thread | Used as BlockAssist's decision hook (see "Scheduling" below) |
| `net.minecraft.client.Minecraft` | `tick()` | Vanilla per-tick update; calls `gameMode.tick()`, input handling, etc. | client thread | Not called directly by mods |

| Class | Member | Purpose |
|---|---|---|

## Rotation

Rotation is plain entity state — there is no separate "server-facing" channel.

| Class | Method | Purpose |
|---|---|---|
| `Entity` | `float getYRot()` / `void setYRot(float)` | Body/view yaw in degrees |
| `Entity` | `float getXRot()` / `void setXRot(float)` | View pitch in degrees, vanilla clamps to [-90, 90] |
| `Entity` | `void setYHeadRot(float)` | Head yaw (kept in sync with `setYRot` for a player looking normally) |
| `net.minecraft.util.Mth` | `wrapDegrees(float)`, `degreesDifference(float from, float to)`, `degreesDifferenceAbs(float, float)` | Angle normalization/interpolation helpers used by vanilla's own turning code (`Entity.turn`, mob look-control) |

Setting `player.setYRot`/`setXRot` **is** the player's real view — the exact
same fields the renderer reads to orient the camera and the exact same fields
`raycastHitResult` reads to aim. There is no way to decouple them in 26.1.2,
and BlockAssist does not attempt to.

## Raycasting / hit results

| Class | Method | Purpose |
|---|---|---|
| `LocalPlayer` | `HitResult raycastHitResult(float partialTicks, Entity cameraEntity)` | The exact call `Minecraft` makes every frame to populate `Minecraft.hitResult`; internally calls `Entity.pick(...)` from the eye position along the current view vector |
| `BlockGetter` (implemented by `ClientLevel`) | `BlockHitResult clip(ClipContext)` | General-purpose line/block raycast, independent of the player's current crosshair — this is what `TargetScanner`/`TargetSelector` use to test line-of-sight to *candidate* blocks the player isn't currently looking at |
| `ClipContext` | constructor `(Vec3 from, Vec3 to, ClipContext.Block, ClipContext.Fluid, Entity)` | `Block.OUTLINE` / `Fluid.NONE` matches vanilla's block-interaction raycast mode |

The crosshair (`Minecraft.hitResult`) only reflects whatever the player is
*currently* looking at. `RotationController` changes `getYRot`/`getXRot`, and
the next frame's vanilla raycast naturally follows — BlockAssist reads
`Minecraft.hitResult` once rotation has converged on the target rather than
short-circuiting the vanilla raycast.

## Block interaction — the real block-breaking lifecycle

Interaction is driven through `net.minecraft.client.multiplayer.MultiPlayerGameMode`
(field `Minecraft.gameMode`), exactly the class real player input goes
through (`Minecraft.startAttack()` / `Minecraft.continueAttack(boolean)`, both
private, called once per client tick from `Minecraft.handleKeyboardInput()`).

| Step | Method | What happens |
|---|---|---|
| 1. Aim | *(vanilla, automatic)* | `Minecraft.hitResult` updated from `LocalPlayer.raycastHitResult` every frame |
| 2. Begin attack | `MultiPlayerGameMode.startDestroyBlock(BlockPos pos, Direction direction)` | Validates (world border, `blockActionRestricted`), sends `ServerboundPlayerActionPacket(Action.START_DESTROY_BLOCK, ...)` wrapped in a client-prediction sequence, resets local `destroyProgress` to 0, calls `state.attack(...)` once, starts the block-breaking overlay via `level.destroyBlockProgress(...)` |
| 3. Continue | `MultiPlayerGameMode.continueDestroyBlock(BlockPos pos, Direction direction)` | Called once per tick while attack is held; accumulates `destroyProgress += state.getDestroyProgress(player, level, pos)` (vanilla hardness/tool-speed formula), plays the periodic hit sound, updates the crack overlay |
| 4. Reach threshold | *(inside `continueDestroyBlock`)* | When `destroyProgress >= 1.0F`: sends `ServerboundPlayerActionPacket(Action.STOP_DESTROY_BLOCK, ...)` and calls `destroyBlock(pos)` |
| 5. Destroy (client prediction) | `MultiPlayerGameMode.destroyBlock(BlockPos pos)` | Re-validates the target, calls `oldBlock.playerWillDestroy(...)`, sets the local block to the post-break fluid/air state, calls `oldBlock.destroy(level, pos, oldState)` — **this is a client-side prediction, applied immediately, before the server responds** |
| 6. Stop/cancel | `MultiPlayerGameMode.stopDestroyBlock()` | Called when the attack key is released or the target changes; sends `Action.ABORT_DESTROY_BLOCK`, clears local destroy state |
| 7. Server confirmation | *(server-authoritative, asynchronous)* | The server independently validates the break and eventually sends its own block-state update. If the server disagrees with the client's prediction, `ClientLevel`'s prediction-reconciliation (`BlockStatePredictionHandler`, keyed by the `sequence` id passed to `startPrediction`) corrects the local state. BlockAssist must not treat step 5 as ground truth — see "Confirmation" below. |

All four gameplay methods above are **public** on `MultiPlayerGameMode`, so
`InteractionController` calls them directly — no mixins needed for basic
interaction.

### Networking generated

- `ServerboundPlayerActionPacket` — `START_DESTROY_BLOCK` / `STOP_DESTROY_BLOCK` / `ABORT_DESTROY_BLOCK`, sent from inside `startPrediction(...)`.
- `ServerboundSetCarriedItemPacket` — sent lazily whenever the held slot changes (`ensureHasSentCarriedItem`), not something BlockAssist needs to send itself.
- Every one of these is wrapped by `MultiPlayerGameMode.startPrediction(ClientLevel, PredictiveAction)`, which opens a `BlockStatePredictionHandler` prediction scope and stamps the packet with a sequence id — this is how the client later reconciles if the server rejects the predicted change. BlockAssist relies on this existing machinery rather than reimplementing packet handling.

### Confirmation — client prediction vs. server truth

`net.fabricmc.fabric.api.event.client.player.ClientPlayerBlockBreakEvents.AFTER`
fires synchronously right after `oldBlock.destroy(...)` inside
`MultiPlayerGameMode.destroyBlock(pos)` (confirmed via the Fabric API mixin
`MultiPlayerGameModeMixin`, injected at the `Block.destroy(...)` invocation
inside `destroyBlock`). This is a **client-predicted** confirmation, not a
server one — it fires the moment the client applies its own predicted break,
before the server has necessarily agreed. BlockAssist's `InteractionStats`
records this as "completed" (client-side), and separately tracks
"confirmed" by observing that the world's actual `BlockState` at that
position stayed non-matching-original on the next tick(s) — if the server
rejects the prediction, `ClientLevel`'s reconciliation will revert the block,
which BlockAssist detects by re-reading `BlockState` and treating a
reversion as a failure, not a confirmation. This distinction (client
predicted vs. still-true-N-ticks-later) is the closest 26.1.2 gets to an
explicit client-visible "the server accepted this" signal without adding
server-side instrumentation (see the README/architecture notes for the
recommended server-side logging described in the project brief).

### Relevant Fabric API events (fabric-events-interaction-v0)

| Event | Purpose |
|---|---|
| `AttackBlockCallback.EVENT` | Cancellable pre-hook fired from `startDestroyBlock`/`continueDestroyBlock` before the vanilla body runs |
| `ClientPlayerBlockBreakEvents.AFTER` | Fired after a block is broken client-side (see above) |
| `UseBlockCallback.EVENT` | Cancellable pre-hook for `useItemOn` (right-click block interaction) |

BlockAssist does not need to hook these directly for the break-only MVP (it
calls `MultiPlayerGameMode` the same way vanilla input handling does, so
these events fire naturally for any other mod/vanilla code listening), but
`ClientPlayerBlockBreakEvents.AFTER` is used directly by `InteractionController`
as the "client predicted a break" signal.

## Scheduling — why BlockAssist's decision cadence is tick-bound

`continueDestroyBlock` is designed to be called **once per client tick**:
each call adds one tick's worth of `getDestroyProgress(...)` to an
accumulator, and the periodic hit sound is gated on `destroyTicks % 4`. The
client's own tick loop already runs at a bounded rate (nominally 20/s;
`Minecraft.tick()` is invoked from the render loop's fixed-timestep
accumulator, not from an uncapped per-frame path). Calling
`startDestroyBlock`/`continueDestroyBlock` more than once per tick would not
reflect any real gameplay action — it would double-count progress against a
formula that was never designed for that and diverge further from what the
server independently computes.

**Decision:** `AutomationController` makes its interaction decisions from
`ClientTickEvents.END_CLIENT_TICK` (client thread, thread-safe world/player
access) and the configurable `actionsPerSecond` is honored as a target
*decision* rate up to the effective tick rate; requesting a rate above ~20/s
does not multiply `MultiPlayerGameMode` calls within a tick — it is logged
and clamped. This keeps interaction indistinguishable from normal input
handling at the API level, per the project's "prefer normal Minecraft
interaction behavior" rule. See the final report for this decision recorded
alongside the alternative that was rejected (driving interactions from a
per-frame render event instead of the tick event).

## Crop maturity

| Class | Member | Purpose |
|---|---|---|
| `net.minecraft.world.level.block.CropBlock` | `static final IntegerProperty AGE` (0-7 for wheat/carrots/potatoes; subclasses like beetroot override `getMaxAge()`) | Growth stage property |
| `CropBlock` | `int getAge(BlockState)`, `int getMaxAge()`, `final boolean isMaxAge(BlockState)` | `isMaxAge` is the correct, block-agnostic maturity check — works for every vanilla `CropBlock` subclass without per-crop special-casing |

`CropAutomation`'s maturity check is simply: block instance is a `CropBlock`
and `((CropBlock) block).isMaxAge(state)` is true.
